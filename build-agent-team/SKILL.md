# Agent Team Builder

## 核心定义

本 Skill 标准化 Claude Code Agent Teams 的创建流程，基于以下设计理念：

```
设计哲学：人工优先，灵活可控

├── 信任人类判断（人工干预、手动触发）
├── 灵活优于严格（软性质量门禁、动态规模建议）
├── 学习式进化（从成功项目提取角色模板）
└── 责任明确（队友自写文档、主队友独占共享文件）
```

---

## 1. 触发规则

### 手动触发（唯一方式）

```
/build-agent-team <你的完整项目需求>
```

**示例**：
```
/build-agent-team 构建一个 Node.js 用户管理 CLI 工具，包含 CRUD、权限控制、数据导入导出
```

## 2. 执行工作流

### 步骤 1：需求收集

如果用户未提供完整信息，**必须询问以下内容**：

> 为了构建优化的 Agent Team，请提供：
> 1. **项目描述**：需要构建/交付/解决的核心问题
> 2. **技术栈**：编程语言、框架、数据库、工具链
> 3. **风险等级**：高风险（核心重构、认证系统）/ 低风险（新功能开发）
> 4. **自定义偏好**：团队规模、特殊约束（可选）

### 步骤 2：场景适配性验证

#### ✅ 适合 Agent Team 的场景

| 场景 | 说明 |
|------|------|
| **并行模块化开发** | 多个独立组件（前端+后端+数据库+测试），无重叠文件编辑 |
| **多维度评审** | 独立视角评审（安全+性能+可维护性+测试覆盖） |
| **竞争性假设调试** | 根因不明确，需要并行验证互斥的故障理论 |
| **跨层协同** | 端到端变更（前端→后端→数据库→基础设施），职责边界清晰 |

#### ❌ 不适合 Agent Team 的场景

使用以下**精确模板拒绝**：

> 该任务不适合使用 Agent Team，原因是 **[具体原因]**。
>
> 建议：使用单个 Claude Code 会话或 subagents，以降低 token 成本和协同开销。

**拒绝原因示例**：
- 具有强依赖的串行任务
- 需要对单个文件进行密集编辑
- 无并行价值的简单常规任务

### 步骤 3：团队结构设计

#### 3.1 团队规模（动态建议）

```
默认规模：4 人
最小规模：3 人
最大规模：5 人（硬限制）

根据任务复杂度动态建议：
├── 简单任务 → 3 人
├── 中等任务 → 4 人
└── 复杂任务 → 5 人
```

#### 3.2 角色映射表

| 任务类型 | 角色配置 |
|---------|---------|
| **全栈功能开发** | 前端工程师、后端工程师、数据库工程师、测试工程师 |
| **PR/代码评审** | 安全评审专家、性能优化评审员、代码可维护性审计师、测试覆盖验证员 |
| **架构/系统设计** | 技术架构师、UX/产品设计师、安全合规专家、反方评审（风险审核） |
| **根因故障调试** | 假设1调查员、假设2调查员、假设3调查员、假设4调查员（每人负责互斥故障理论） |

#### 3.3 文件所有权规则（零冲突保证）

```
强制要求：每个队友拥有排他、无重叠的文件/目录所有权

示例：
├── 前端工程师 → src/frontend/ (排他)
├── 后端工程师 → src/backend/ (排他)
├── 数据库工程师 → src/database/ (排他)
└── 测试工程师 → test/ (排他)

共享文件处理：由核心队友（如后端）统一管理，其他队友通过接口调用
```

#### 3.4 角色冲突验证（创建时强制）

```
在创建团队时必须验证：
├── 检查角色定义是否存在职责重叠
├── 检查文件所有权是否存在冲突
└── 发现问题则拒绝创建，提示用户修正
```

## 3. 强制团队配置

### 3.1 团队负责人职责

```
协调者 + 决策者（不承担集成和问题解决）

├── 将项目拆解为独立、无重叠的任务
├── 为对应队友分配任务
├── 评审并批准/拒绝高风险计划
├── 合成所有队友的最终交付结果
├── 管理完整的团队生命周期
└── 解决跨队友的协同问题

禁止：直接编写任何代码
```

### 3.2 质量门禁（软性警告）

```
任务完成时运行检查，但允许标记完成

├── 代码规范检查（ESLint/Prettier）
├── 单元测试覆盖率 >= 80%
├── 安全漏洞扫描
└── 文档完整性检查

未通过检查的问题 → 记录到技术债务任务
```

### 3.3 Token 成本控制

```
├── 禁止广播消息（仅允许点对点通信）
├── 每队友最多 5-6 个任务
├── 团队规模上限 5 人
├── 队友仅加载相关上下文
└── 发送消息前自检必要性
```

### 3.4 通信协议

#### 结构化消息格式

```json
{
  "type": "task_update | dependency_request | blocking_alert | completion_notice",
  "priority": "low | medium | high | critical",
  "requires_response": true,
  "sender": "队友名称",
  "recipient": "目标队友 | team_lead",
  "content": "消息正文",
  "metadata": {
    "task_id": "关联任务ID",
    "files_affected": ["影响的文件列表"]
  }
}
```

#### 发送前自检

```
□ 这条消息是否真的必要？
□ 收件人是否能处理这个问题？
□ 消息是否包含了足够的上下文？
□ 是否可以通过任务列表更新代替？
```

### 3.5 任务依赖管理

```
动态协商机制：

├── 队友之间实时协调依赖关系
├── 发现阻塞时主动通知相关队友
├── 阻塞超时（默认 30 分钟）→ 自动重新分配依赖任务
└── 通过任务列表的 blockedBy 显式声明依赖
```

### 3.6 失败恢复

```
人工干预机制：

├── 检测到队友失败（token 限制、API 错误等）
├── 通知团队负责人
├── 负责人决定：重启队友 / 重新分配任务 / 调整计划
└── 保留已完成工作的上下文
```

### 3.7 生命周期管理

```
启动 → 运行 → 完成 → 关停 → 清理 → 通知

1. **记录开始时间** → `START_TIME=$(date +%s)`
2. 创建团队和任务列表
3. 分配任务给队友
4. 队友完成任务并通知
5. 所有任务完成 → 向队友发送关停请求
6. 队友确认关停 → 执行团队清理
7. **发送完成通知** → 语音播报 + 系统通知（含项目名、阶段、耗时）
```

## 项目背景与核心目标

构建生产级 Node.js 用户管理 CLI 工具，核心功能包括：
- 用户增删改查
- 基于角色的权限控制
- JSON 数据导入导出
- ESLint 规范合规
- 完整的单元/集成测试覆盖

**技术栈**：Node.js、Commander.js、Jest、ESLint（Airbnb 规范）
**风险等级**：中风险（认证/权限逻辑为高风险）

## 团队核心配置

### 团队负责人规则

团队负责人（主会话）仅可执行以下协调任务，**绝对不可直接编写代码**：

1. 将项目拆解为独立、无重叠的任务
2. 为对应队友分配任务
3. 评审并批准高风险任务的实施计划
4. 合成所有队友的最终交付结果
5. 管理完整的团队生命周期
6. 解决跨队友的协同问题

### 高风险任务规则：实施前计划审批

针对所有高风险任务（认证/授权逻辑）：

1. 负责的队友**必须在编写任何代码前**提交详细实施计划
2. 计划必须包含：代码结构、变更范围、安全影响、测试计划、回滚策略
3. 团队负责人评审计划，满足要求才可批准
4. 计划批准前，队友不可开始实施

### 质量门禁（软性警告）

任何任务标记完成前，应满足以下要求：

- 代码遵循 ESLint Airbnb 规范
- 单元测试覆盖率 >= 80%
- 安全漏洞扫描无高危问题
- 功能有完整注释和文档

**未满足的问题记录到技术债务任务**

### Token 成本控制

1. 禁止广播消息，仅允许点对点通信
2. 每队友最多 5-6 个任务
3. 团队规模严格限制
4. 发送消息前自检必要性

### 生命周期管理

1. 所有任务完成 → 向队友发送关停请求
2. 队友确认关停 → 执行团队清理
3. 仅团队负责人有权执行清理

## 队友角色分配

### 队友1：CLI 前端开发工程师

- **核心职责**：所有用户侧 CLI 交互逻辑
- **聚焦领域**：CLI 命令结构、参数解析、用户输入输出、错误消息、UX 流程
- **要求交付物**：CLI 交互代码、单元测试、使用文档
- **排他所有权**：`src/cli/` 目录
- **专属指令**：
  - 使用 Commander.js 进行 CLI 参数解析
  - 所有命令必须包含帮助文本和使用示例

### 队友2：后端核心逻辑工程师

- **核心职责**：用户管理和权限控制的核心业务逻辑
- **聚焦领域**：用户 CRUD、角色访问控制、业务规则、数据校验
- **要求交付物**：业务逻辑代码、单元测试、流程文档
- **排他所有权**：`src/core/` 目录
- **专属指令**：
  - 权限控制逻辑实现前必须提交计划并获得审批
  - 所有用户输入必须消毒，防止注入攻击
- **共享文件管理**：统一管理 `src/shared/` 中的共享类型和工具

### 队友3：数据层工程师

- **核心职责**：数据持久化、存储和导入导出
- **聚焦领域**：数据模型设计、JSON 文件存储、数据导入导出、文件 I/O
- **要求交付物**：数据层代码、单元测试、数据模型文档
- **排他所有权**：`src/data/` 目录
- **专属指令**：
  - 使用本地 JSON 文件存储
  - 所有文件操作必须有错误处理和回滚能力

### 队友4：测试与质量保障工程师

- **核心职责**：测试、代码质量验证和安全扫描
- **聚焦领域**：集成测试、ESLint 规范执行、安全扫描、测试覆盖度
- **要求交付物**：集成测试套件、安全扫描报告、ESLint 验证结果、质量签字
- **排他所有权**：`test/` 目录
- **专属指令**：
  - 所有代码必须通过 ESLint 验证和安全扫描
  - 满足 80% 测试覆盖率才可标记完成

## 任务管理规则

1. 任务拆解为独立、自包含的单元
2. 明确任务依赖关系，被阻塞任务不可认领
3. 任务状态：待处理 → 进行中 → 已完成
4. 队友完成任务后发送任务级通知
5. 阻塞超时（30 分钟）自动重新分配依赖任务

## 最终完成标准

项目仅在以下条件全部满足时标记为完成：

1. 所有交付物 100% 完成
2. 所有任务通过质量门禁（或已记录技术债务）
3. 所有队友已优雅关停
4. 团队负责人已合成并归档最终结果
5. **发送任务完成通知**（语音播报 + 系统通知）：
   ```bash
   # 计算耗时
   END_TIME=$(date +%s)
   DURATION=$((END_TIME - START_TIME))
   MINUTES=$((DURATION / 60))
   SECONDS=$((DURATION % 60))

   # 生成标题（包含项目名、阶段、耗时）
   TITLE="✅ ${项目名称} - ${当前阶段} (${MINUTES}分${SECONDS}秒)"
   MESSAGE="Agent Team 任务已全部完成"

   # 发送通知
   (say "$MESSAGE" &) && terminal-notifier -title "$TITLE" -message "$MESSAGE"
   ```

   **标题示例**：
   - 「✅ 用户管理CLI - 开发完成 (15分32秒)」
   - 「✅ 支付系统 - 测试通过 (8分45秒)」
   - 「✅ 数据迁移 - 部署完成 (3分20秒)」
